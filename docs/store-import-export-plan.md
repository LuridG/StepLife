# StepLife 生活记录 导入/导出 + 账单智能导入 方案 v1.0

> 版本：v1.0 讨论稿（2026-08-04）
> 状态：P0-P4 已完成代码实施并通过 `flutter analyze` + `flutter test`（2026-08-04）；P5 模板差异化适配、P6 收尾待后续迭代
> 范围：生活记录（Store Journal）数据导出 / 模板化导入 / 模拟导入（Dry-run）/ 账单 OCR + AI 智能导入

## 0. 用户诉求汇总

1. 生活记录需要「数据导入/导出」能力，导出支持**单分类**与**全量**两种粒度。
2. 图片本期**不导出**（文件体积与跨设备还原成本高），但导出结构保留图片字段位，为将来 zip 带图方案预留接口。
3. 导入采用**模板化 JSON**，默认「新建」、弹窗内可切换「合并」，绝不破坏现有数据。
4. 导入需要**模拟导入（Dry-run）**：先看导入结果预览，不满意可当场调整（勾选/改金额/改时间/改名称/切换新建或合并），确认后才真正落库。
5. 导入要**分上下文层级**：详情页导入=纯打卡追加；识别到新店铺/新片名的导入=先建客观项目再打卡；顶栏导入标准 JSON=全量模板导入。
6. 提供**账单智能导入**：微信消费账单截图 → 离线 OCR 识别 → DeepSeek 整理成结构化打卡 → 预览确认后落库。
7. 不同模板导入行为差异化（美食/影视/菜篮子/零食等），第一版先做通用骨架，逐模板精修。

## 1. 现状与可行性结论

- 生活记录数据位于 SQLite `steplife_v9.db`，核心表：`store_categories`（分类+模板）、`store_items`（项目+`extrasJson`）、`store_logs`（打卡+`cost`+成员+菜单+分钟级时间）、`store_menu_items`（餐饮菜单）。
- 当前**没有**任何细粒度导入/导出能力：仅有 WebDAV 整库备份/恢复（快照+图片增量），以及影视模板的 TMDB 元数据导入（非用户数据）。
- 项目无 `share_plus` / `file_picker` / OCR 依赖，需要新增（见 §4）。
- 数据层结构清晰，导入导出**不需要改表结构**，符合「数据库非破坏迁移」红线。

## 2. 导出设计

### 2.1 粒度与入口

| 粒度 | 入口 | 输出文件 | 内容范围 |
| --- | --- | --- | --- |
| 单分类 | 分类浏览页菜单「导出该分类」 | `steplife_store_category_{分类名}_{日期}.json` | 该分类 + 其下全部项目/打卡/菜单 |
| 全量 | 生活记录顶栏菜单「导出全部」 | `steplife_store_export_all_{日期}.json` | 全部分类/项目/打卡/菜单 |

### 2.2 JSON 格式 v1（核心 Schema）

```json
{
  "schemaVersion": 1,
  "exportType": "category | full",
  "sourceAppVersion": "1.6.0+20260804",
  "exportedAt": "2026-08-04 12:00",
  "categories": [
    { "id": 1, "name": "餐厅", "iconName": "storefront", "templateKey": "dining", "extraFieldsJson": "[]" }
  ],
  "items": [
    {
      "id": 101, "name": "老街小馆", "category": "餐厅", "rating": 4.5,
      "images": [],
      "address": "中山路 12 号", "notes": "招牌红烧肉",
      "extrasJson": "{\"brand\":\"\"}", "createdAt": "2026-06-01 10:00"
    }
  ],
  "logs": [
    {
      "id": 9001, "storeName": "老街小馆", "cost": 128.5,
      "visitorIdsJson": "[]", "visitorNamesJson": "[\"我\"]",
      "memo": "红烧肉不错", "extrasJson": "{}",
      "menuItemIdsJson": "[]", "menuNamesJson": "[\"红烧肉\"]", "menuSpecsJson": "[\"大份\"]",
      "timestamp": "2026-07-28 12:30"
    }
  ],
  "menuItems": [
    { "id": 501, "storeId": 101, "name": "红烧肉", "spec": "大份", "price": 68.0 }
  ]
}
```

### 2.3 导出规则

- 时间戳一律为分钟级 `yyyy-MM-dd HH:mm`，原样导出、原样导入，与「打卡时间语义」红线一致。
- `extrasJson` 等 JSON 字段**原样保留**，不解析不加工（菜篮子品牌/单位、影视集数等不丢失）。
- `images` 字段位恒为 `[]`；导出器封装 `StoreExporter`，预留 `includeImages` 参数与图片清单钩子，将来切换 zip 带图无需改 Schema。
- 导出不修改任何数据库内容，纯读操作。

### 2.4 落盘与分享

- 导出文件先写入应用缓存目录，再用系统分享面板（`share_plus`）分享（可存微信/文件管理器/其他设备）。
- 同时复制一份到应用文档目录留底，弹窗提示完整路径。
- 桌面端（Windows）无系统分享面板时降级为「打开所在目录」或直接提示路径。

## 3. 导入设计

### 3.1 导入分级（按入口自动流转）

| 层级 | 触发入口 | 数据形态 | 行为 |
| --- | --- | --- | --- |
| L1 纯打卡导入 | 项目详情页「导入打卡记录」 | 只有金额/日期/内容（账单或 JSON 记录片段） | 上下文已知目标项目，仅追加打卡记录，**绝不新建项目** |
| L2 新建项目+打卡 | 分类浏览页/顶栏导入，且数据含新店铺/新片名 | 识别到名称+分类+记录 | 先进入「新建项目确认」，可改名称/分类/模板，确认后建项目再追加打卡 |
| L3 模板全量导入 | 顶栏「导入」选择标准 JSON | 完整 Schema（分类/项目/打卡/菜单） | 校验 → 模拟导入预览 → 默认新建/可切合并 → 落库 |

### 3.2 导入流程（所有层级统一骨架）

```
选文件/选图 → 解析（JSON 校验 或 OCR+AI）
  → 生成导入草稿 ImportDraft（纯内存，不写库）
  → 模拟导入页预览（可编辑，见 §5）
  → 用户确认
  → 自动备份当前库（沿用最近 3 份机制）
  → 单事务落库（失败回滚）
  → 结果报告（新建 X 分类 / Y 项目 / Z 打卡，失败清单）
```

### 3.3 校验规则（L3 JSON）

- `schemaVersion` 必须等于 1；未知版本直接拒绝并提示「文件版本过新」。
- 必填字段缺失/类型错误/时间格式非法 → 报错到具体条目（如 `logs[3].timestamp 格式非法`）。
- 分类名/项目名去重规则：同一导入文件内重名视为异常；与库内重名由「新建/合并」策略决定。

### 3.4 落库策略

- **新建（默认）**：库内已有同名分类 → 新分类名加 `(导入)` 后缀；项目在目标分类下按名称新建；打卡全部作为新记录插入（保留原始时间戳）。
- **合并**：按 `分类名 + 项目名` 精确匹配；匹配成功 → 打卡记录追加到该项目、`store_menu_items` 按 `name+spec` 去重合并；匹配失败 → 按新建逻辑处理。
- 每个分类可在模拟导入页单独选择「新建/合并」，默认跟随全局策略。

### 3.5 模板文件

- 导入弹窗提供「查看模板格式」，内置一份与 §2.2 Schema 完全一致的示例（可复制/可导出为 `.json`）。
- 模板供手动填写或供 AI/外部工具按规范生成。

## 4. 新增依赖与文件结构

### 4.1 依赖

| 包 | 用途 | 说明 |
| --- | --- | --- |
| `share_plus` | 导出分享 | 系统分享面板 |
| `file_picker` | 导入选文件 | 选 JSON |
| `google_mlkit_text_recognition` | 账单离线 OCR | 中文识别，无需联网，包体略增 |

### 4.2 新文件

```
lib/core/export_import/
  store_exporter.dart            // 导出器：单分类/全量 JSON，预留 includeImages 钩子
  store_importer.dart            // 解析+校验 JSON → ImportDraft
  import_draft.dart              // 导入草稿模型（可编辑状态）
  import_preview_screen.dart     // 模拟导入页（预览/编辑/确认）
  bill_parser.dart               // 账单解析编排：ML Kit OCR → DeepSeek 结构化 → BillDraft
lib/features/assistant/services/
  bill_structure_prompt.dart     // 账单整理 Prompt（复用 deepseek_service）
```

### 4.3 接入入口

- 项目详情页菜单：导出、导入打卡记录（L1）、导入账单（OCR+AI）。
- 分类浏览页菜单：导出该分类（L1 场景的 JSON 片段）；若内容含新店铺名走 L2。
- 生活记录顶栏菜单：导出全部 / 导入 JSON（L3）。

## 5. 模拟导入（Dry-run）交互设计

- 解析完成后**不落库**，进入「模拟导入」页，全程内存计算：
  - **顶部摘要**：识别到 X 条记录 / Y 个新项目 / Z 个新分类；若 AI 识别出店铺/片名，这里显示「识别名称：XXX」可改名，分类/模板可下拉调整。
  - **记录列表**：每条一行，字段对齐（金额/时间/备注），**可勾选**、**可编辑金额/时间/memo**，编辑后摘要实时更新。
  - **归属**：命中已有项目时显示「将合并到：XXX」，可切换为「新建」。
  - **操作**：底部「确认导入」按钮；确认前先备份 → 单事务写入 → 失败回滚；完成后给结果报告。
- 预览页不碰数据库，用户调整后「确认导入」的真实结果与预览完全一致。

## 6. 账单智能导入（OCR + AI）

### 6.1 流程

```
项目详情页「导入账单」→ image_picker 选图
  → google_mlkit 离线 OCR 提取全部文本
  → DeepSeek（deepseek-v4-flash）结构化整理
  → 返回 {"records":[{"amount":12.5,"time":"2026-07-28 12:30","memo":"微信支付-餐饮"}], "storeGuess":{...}}
  → 模拟导入页预览 → 确认落库
```

### 6.2 AI 整理规则

- 复用现有 `deepseek_service`（`deepseek-v4-flash`，Key 存 `app_settings`），新增专门 Prompt（`bill_structure_prompt.dart`），要求**只返回结构化 JSON**。
- 上下文注入：OCR 全文 + 当前项目名/分类/模板 + 今天日期。
- 字段提取：`amount`（金额，必须数字）、`time`（分钟级，缺失时按今天推断并标记「推测」）、`memo`（账单中出现的消费内容/菜名，**有则写入，无则省略**）。
- 店铺识别：L1 上下文已确定店铺，不再询问；L2 场景输出 `storeGuess`（名称/分类/模板建议），进入新建项目确认。
- 红线：AI 只产出结构化建议，**所有动作经用户确认后才落库**（延续智能助手红线）。

### 6.3 OCR 注意

- `google_mlkit_text_recognition` 使用设备端模型，识别语言优先中文，不联网。
- 识别结果空/过低置信度 → 提示用户重新拍摄，保证光线与清晰度。
- 解析失败不写任何数据。

## 7. 模板差异化适配（通用骨架先行，逐模板精修）

| 模板 | L1 纯打卡 | L2 新建 | 备注 |
| --- | --- | --- | --- |
| dining 餐饮 | cost/time/memo，识别到菜名联动 `store_menu_items` | 新建餐厅+打卡 | 菜单价格可一并入库 |
| snack 零食 | cost/time/memo | 新建零食项目+打卡 | 品牌入 `extrasJson.brand` |
| basket 菜篮子 | cost/数量/单价/单位 → 价格打卡 | 新建「品类+品牌」 | 复用 `extrasJson` 品牌/单位 |
| movie 影视 | 观看打卡（日期/集数入 extras） | 匹配或新建影片（复用 TMDB 可选） | 集数/状态等字段原样保留 |
| shopping/book/place/generic | cost/time/memo | 新建项目+打卡 | 通用字段 |

- 第一版实现通用落库骨架（extras 原样保留），逐模板字段联动放后续迭代。

## 8. 安全红线（必须遵守）

1. **非破坏**：不改表结构；导入前自动备份当前库（沿用最近 3 份机制），失败可回滚。
2. **AI 不直接写库**：OCR/AI 输出仅作为建议，用户确认后才落库。
3. **时间语义**：导入打卡保留原始分钟级时间戳，展示仍按时间倒序（新→旧）。
4. **图片不导入**：本期 `images` 恒空；将来 zip 方案需将图片复制进应用缓存目录后再存路径（沿用现有图片规范）。
5. **WebDAV 同步**：本方案不改表结构，无需更新 `_syncTables`；若后续新增表必须同步备份清单。
6. **不覆盖用户数据**：新建/合并策略均不允许删除或覆写现有记录。

## 9. 分阶段实施计划

| Phase | 内容 | 验收标准 |
| --- | --- | --- | --- |
| P0 依赖与导出 | 新增 3 依赖；`StoreExporter` 单分类/全量 JSON；顶栏与分类页入口；分享/留底 | 导出文件与 §2.2 Schema 一致，`flutter analyze` 0 错误 |
